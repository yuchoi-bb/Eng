# 영어 쉐도잉 앱 — 요구사항 명세 (SRS)

- **버전**: v0.3 (초안)
- **작성일**: 2026-09-15
- **플랫폼**: Android (Kotlin / Jetpack Compose), 태블릿 다중 기기
- **배포**: 개인용. Play Console **내부 테스트 트랙** 배포 (공개 스토어 출시 없음)
- **대상 사용자**: 본인 1인 (CEFR A1~A2, 영어 왕초보)

---

## 1. 제품 개요

**유튜브 영어 쉐도잉 쇼츠를 기본 소재로**, **내 발음**과 **학습 횟수**를 카운트하는 앱.

숏폼 영상(60초 이하)의 같은 문장을 반복해서 소리 내어 말하고(쉐도잉), 하루 목표 발화량을
채우는 것을 핵심 루프로 삼는다.

| 축 | 무엇을 카운트하나 | 근거 절 |
|---|---|---|
| **학습 횟수** | 문장 1개 = 1카운트. 단, **3단계(듣기→보고 말하기→자막 끄고 말하기) 완주**가 1카운트 | 4.3, 7.2 |
| **발음** | 내 녹음을 문장 텍스트와 대조한 점수 (L2 텍스트 일치도 → L3 발음·억양) | 6 |

**기본 소재는 유튜브 쇼츠(F-1)다.** 업로드 경로(F-2)는 유튜브에 없는 영상을 쓰기 위한
보조 경로이며, 개발 중에는 프록시 없이 파이프라인을 검증하는 수단으로도 쓴다.

### 1.1 핵심 루프

```
유튜브 쇼츠 공유 → 스크립트 자동 추출 → 문장 단위 반복 발화 → 일일 예산 달성
                                          │
                                          └─ 녹음 → L2 즉시 판정(카운트) + L3 비동기 발음 점수
```

## 3. 영상 소스 (2종)

### F-1. 유튜브 쇼츠

| 항목 | 내용 |
|---|---|
| 입력 | 유튜브 앱 → 공유 → `ACTION_SEND` (text/plain) |
| 스크립트 | Gemini에 URL 직접 전달 (`{"type":"video","uri":"<youtube-url>"}`) |
| 재생 | 공식 IFrame Player 임베드 (androidyoutubeplayer 라이브러리) |
| 미디어 저장 | **없음** (앱은 URL과 텍스트만 보관) |

**제약**
- 공개 영상만 가능. 비공개·미등록(unlisted) 불가
- 무료 등급: 1일 8시간 분량 상한 / 유료 등급: 길이 제한 없음
- 유튜브 URL 입력은 **프리뷰 단계**이며 현재 무료. 가격·레이트리밋 변경 가능성이 공식 문서에 명시됨
  → **프록시에 사용량 계측을 v1부터 포함할 것**
- 원본 오디오 파일 추출 불가 → **원본 화자의 파형과 내 발음을 음향적으로 겹쳐 보는 기능만** 불가.
  L1 A/B 비교는 IFrame Player의 구간 재생으로 대체한다 (정밀도는 초 단위 + ±300ms 패딩)
- **L2·L3 발음 채점은 이 경로에서도 정상 동작한다.** 채점 입력은 원본 오디오가 아니라
  `내 녹음 + 기준 텍스트`이고, 기준 텍스트는 이 경로가 이미 생성한다 (6절 참조)

### F-2. 녹화 영상 업로드

| 항목 | 내용 |
|---|---|
| 입력 | Photo Picker(`PickVisualMedia`) 또는 `ACTION_SEND` (video/*) |
| 전처리 | MediaExtractor로 오디오만 m4a 추출 (FFmpegKit 비사용 — 유지보수 중단) |
| 스크립트 | `gemini-3.5-transcribe`, 단어 단위 타임스탬프 활성화 |
| 재생 | ExoPlayer 로컬 재생 |
| 저장 | 원본 복사 없이 URI persistable 권한만 보유 |

**설계 원칙**: 영상 전체가 아닌 **오디오만 전송**. 토큰 비용 절감. 100MB 미만은 inline, 초과 시 Files API.

**이점**: 오디오 추출이 가능하므로 원본 화자와의 **음향 비교**(파형 대조, 화자별 억양 모사)가
가능하다. 단 **L2·L3 발음 채점은 두 경로 모두에서 지원된다** — 채점은 원본 오디오가 아니라
기준 텍스트를 쓰기 때문이다 (6절).

## 4. F-3. 반복 말하기 (예산 기반)

### 4.1 설계 결정 — 목표는 2층 구조

시간과 횟수를 **서로 다른 계층의 목표**로 둔다. 같은 층에 두면 "둘 다 채워야 하나 / 하나만 채우면 되나" 충돌이 생기지만, 층을 나누면 둘 다 설정해도 모순이 없다.

| 계층 | 설정값 | 의미 |
|---|---|---|
| **영상 단위** | `targetReps` | 이 영상을 몇 번 말할 것인가 |
| **하루 단위** | `dailyTargetSec` | 오늘 총 몇 분 말할 것인가 |

하루 목표는 여러 영상의 발화 시간이 **누적되어** 채워진다.

### 4.2 횟수 설정 (영상 단위)

`autoReps` 토글로 두 방식 중 선택:

| 모드 | 동작 |
|---|---|
| **자동** (기본) | 아래 계산식으로 산출한 값을 제시 |
| **수동** | 사용자가 직접 입력한 고정 횟수 사용 (예: 무조건 30회) |

자동 모드 계산식:

```kotlin
videoSpeechSec = lastWordEnd - firstWordStart      // 전사 결과의 부산물, 추가 호출 없음
suggestedReps  = ceil(dailyTargetSec / videoSpeechSec).coerceIn(5, 50)
```

| 영상 유형 | 발화 길이 | 자동 제시 횟수 |
|---|---|---|
| 일반 쇼츠 | 40초 | 8회 |
| 한 문장 영상 | 8초 | 38회 |

자동 모드에서도 제시값은 **세션 시작 화면에서 사용자가 덮어쓸 수 있다.**

### 4.2.1 시간 설정 (하루 단위)

- `dailyTargetSec` 기본값 **300초(5분)**, 온보딩에서 5/10/15분 중 선택
- 영상 1개로 못 채우면 **2번째 영상을 자동 제안**
- **상한이 아니라 목표값**이다. 수동 횟수를 크게 잡아 초과해도 차단하지 않고 달성률 120% 등으로 표시
- 적응 로직(4.7)의 완료율은 **시간 기준**으로만 계산한다 (수동 횟수는 사용자 의도이므로 자동 조정 대상에서 제외)

### 4.3 카운트 단위

- 단위는 **문장(utterance) 1개**로 통일
- "영상 전체 1회"는 문장 수만큼 카운트로 환산
- → 1문장 영상과 5문장 영상이 동일 통계에 집계됨

### 4.4 영상 유형별 반복 방식

전사 시 Gemini가 함께 분류하여 반환:

| type | 의미 | 반복 방식 |
|---|---|---|
| `DRILL` | 같은 문장을 여러 번 말하는 영상 | 원본이 이미 반복 구조 → reps × 0.5 |
| `SINGLE` | 긴 문장을 한 번만 말하는 영상 | 호흡 단위로 분할 → 부분 반복 후 전체 통과 1회 |
| `DIALOGUE` | 대화형 | 문장별 N회 → 전체 통과 M회 |

### 4.5 세션 동작

- 카운트 트리거: **녹음 종료 → 자동 +1 → 즉시 다음 회차 재생** (탭 불필요, 무한 루프 모드)
- UI: 세그먼트 링 진행바 + 남은 횟수
- 세션 중 `FLAG_KEEP_SCREEN_ON` 유지
- 녹음 파일은 **최근 3회분만 보관 후 순환 삭제** (용량 폭증 방지)
  - **예외**: 각 문장의 **최초 녹음 1개는 영구 보관** (F-9 성장 기록용)

### 4.6 날짜 처리

> **자정 WorkManager로 롤오버하지 않는다.**
> 절전 모드·기기 시간 변경 시 누락된다. 조회 시점에 `LocalDate` 키로 판정한다.

### 4.7 콜드스타트 & 적응

1. **온보딩**: 목표 시간만 선택 (5 / 10 / 15분) → 예산 초기화. 개인화 판단 없이 시작
2. **3일차부터 적응**:
   - 완료율 ≥ 100% → 예산 +10%
   - 완료율 < 60% → 예산 −20%
   - 일일 변화폭 ±20%로 클램프

## 5. F-4. 쇼츠 추천

### 5.1 설계 결정

> **LLM에 영상 추천을 맡기지 않는다.** 존재하지 않는 영상 ID를 생성한다(환각).
> 실제 영상 목록은 YouTube Data API v3로만 확보한다.

**쿼터 제약**: 프로젝트당 1일 10,000 units, `search.list` 1회당 100 units → **1일 약 100회 검색이 한계**.
사용자 요청마다 호출하면 소수 사용자에서 즉시 고갈 → **서버 배치 + 앱은 조회만** 구조가 필수.

### 5.2 2계층 구조

**서버 배치 (1일 1회, 오프라인)**

1. ESL 채널 화이트리스트 기반 `playlistItems.list` (1 unit) — `search.list` 대신 사용
2. `videos.list`로 60초 이하 필터 (50개 배치, 1 unit)
3. Gemini 난이도 분류 → `{cefr, wpm, sentenceCount, topic}`
4. **A1/A2 + WPM 120 이하**만 추천 풀에 저장

**앱 런타임**

- 서버 풀 조회만 수행. YouTube API 직접 호출 **0회**
- 개인화는 로컬 정렬: 완료율 · 재생속도 · 실패 문장 이력 기준

### 5.3 채널 화이트리스트

키워드 검색보다 품질이 안정적. 왕초보용 ESL 채널 **10~20개**로 시작.

## 6. 난이도 3단계 (점증)

| 레벨 | 기능 | 구현 | 비용 |
|---|---|---|---|
| **L1** | 구간 반복 + 내 녹음 A/B 비교 | 로컬 | 0 |
| **L2** | 텍스트 일치도 채점 | Android `SpeechRecognizer` (온디바이스) | 0 |
| **L3** | 발음·억양 점수 | Azure Pronunciation Assessment (프록시 경유) | **사실상 0** (아래 6.2) |

**L2 채점 방식 (왕초보 대응)**

> WER을 그대로 쓰면 왕초보는 매번 40~60% 오답으로 표시되어 3일 내 이탈한다.
> **핵심 단어 매칭 기반 부분 점수**를 사용한다. (예: 핵심 단어 3개 중 2개 = 67점)

### 6.1 L3는 원본 오디오를 쓰지 않는다 (초안 정정)

> v0.2 초안은 "유튜브 소스는 오디오 추출 불가 → L3는 업로드 경로에서만 지원"이라고 적었다.
> **이 제약은 성립하지 않는다.** 발음 채점의 입력은 다음 둘이다.
>
> | 입력 | 출처 |
> |---|---|
> | 학습자 녹음 | 기기 마이크 — 4.5절에서 이미 녹음하고 있다 |
> | 기준 **텍스트** | 전사 결과의 `sentences[].text` — F-1도 생성한다 |
>
> 원어민의 *특정 녹음*은 필요 없다. `accuracy`는 음소 모델과 대조하고, `completeness`는
> **기준 텍스트 대비** 발음된 단어 비율로 정의된다. 따라서 **L3는 유튜브 경로에서도 동작한다.**
>
> 원본 오디오가 없어서 실제로 못 하는 것은 하나뿐이다 — **그 영상 화자의 파형·억양과
> 내 발음을 직접 겹쳐 보는 기능.** 이것은 L3(절대 기준 채점)가 아니라 별개의 v2 기능이다.

### 6.2 비용

Pronunciation Assessment는 Speech-to-Text Standard 요금으로 과금된다.

| 항목 | 값 |
|---|---|
| 무료 등급 F0 | **월 5 오디오 시간** |
| 초과분 | 시간당 약 **$1.32** |
| 일일 목표 300초(8절) 기준 소모량 | 월 **2.5시간** → **F0 안에 들어온다** |
| 목표를 10분으로 올린 경우 | 월 5시간 → F0 경계 |
| 목표를 15분으로 올린 경우 | 월 7.5시간 → 초과 2.5시간 × $1.32 = **월 $3.3** |

1인 사용에서는 사실상 무료다. **L3를 v2로 미룰 비용상의 이유가 없다.**

### 6.3 L2와 L3의 역할 분담

둘 중 하나를 고르는 것이 아니라 **다른 시점에 쓴다.**

| | L2 (온디바이스) | L3 (Azure, 프록시 경유) |
|---|---|---|
| 시점 | 매 발화, **동기** | 배경 **비동기** |
| 역할 | 4.5절 무한 루프의 진행 판정 (다음 회차로 넘어갈지) | 발음 품질 기록 |
| 지연 | 0 | 네트워크 왕복 |
| 오프라인 | 동작 | 큐에 쌓아 두었다 나중에 전송 |

> **L3를 동기 경로에 두면 안 된다.** 4.5절은 "녹음 종료 → 자동 +1 → 즉시 다음 회차 재생"의
> 무한 루프다. 여기에 네트워크 왕복을 끼워 넣으면 루프의 리듬이 끊긴다.
> L2가 즉시 판정해 루프를 돌리고, L3 점수는 도착하는 대로 화면에 채워 넣는다.

### 6.4 아키텍처 영향

Azure 키도 APK에 넣지 않는다 (9.2절 원칙과 동일). **프록시가 Gemini에 더해 Azure Speech도
중계**해야 한다. 녹음 파일이 프록시를 통과하므로 9.2절의 스트리밍 패스스루 설계가 여기에도 적용된다.

## 7. 학습 지속 기능 (F-6 ~ F-9)

> **설계 배경**: 영상 하나를 반복하고 나면 다시 만나지 않는 구조에는 구멍이 있다.
> 왕초보는 하루 반복만으로 문장이 남지 않으며, 망각 주기에 맞춰 재노출하는 장치가 없으면 한 달 뒤 잔존 학습량이 거의 0에 수렴한다.

### 7.1 F-6. 복습 큐 (SRS) — v1

| 항목 | 내용 |
|---|---|
| 수집 | L2 채점에서 **오답 처리된 문장만** 자동 등록 |
| 간격 | 1일 → 3일 → 7일 → 14일 (통과 시 다음 단계, 실패 시 1일로 리셋) |
| 제시 | 세션 시작 시 "복습 N문장 + 신규 영상" 혼합 |
| 비용 | **Room만으로 구현. API 호출 0** |

복습 문장의 발화 시간도 `achievedSec`에 합산한다.

### 7.2 F-7. 쉐도잉 3단계 모드 — v1

왕초보가 처음부터 따라 말하면 입이 따라가지 못한다. 문장마다 단계를 나눈다.

| 단계 | 동작 | 자막 |
|---|---|---|
| 1 | 듣기만 | 표시 |
| 2 | 보면서 따라 말하기 | 표시 |
| 3 | 자막 끄고 따라 말하기 | 숨김 |

**3단계를 모두 통과해야 카운트 1회로 인정한다.** 이 규칙이 반복 횟수의 질을 결정한다.

> 4.3절의 카운트 단위(문장 1개 = 1카운트)는 유효하되, "1카운트 = 3단계 완주"로 정의가 구체화된다.

### 7.3 F-8. 표현 은행 — v2

- 전사 결과에서 **빈출 표현(chunk) 추출** — 별도 API 호출 없이 전사 응답에 필드 추가
- 여러 영상에 **3회 이상 등장한 표현**을 랭킹으로 누적
- 왕초보에게는 단어 단위보다 덩어리 표현이 학습 효율이 높음

### 7.4 F-9. 녹음 성장 기록 — v2

- 같은 문장의 **최초 녹음과 현재 녹음을 나란히 재생**
- 점수 지표보다 이탈 방지 효과가 직접적임 ("늘고 있는지 모르겠다"가 주요 이탈 사유)
- 4.5절 녹음 보관 예외 규칙에 의존

## 9. 아키텍처

### 9.1 앱

- Kotlin / Jetpack Compose (태블릿 대응 adaptive layout)
- **Firestore + 오프라인 퍼시스턴스** — 로컬 캐시와 기기 간 동기화를 동시 해결
  - Room 대신 채택. 태블릿 3대 동기화를 자체 구현하면 충돌 해결 로직을 직접 만들어야 함
  - 단일 사용자라 동시 편집이 없으므로 **기본 Last-Write-Wins로 충분**
- **WorkManager 큐** — 전사 요청 재시도 (장시간 API 호출이라 Firestore 오프라인 쓰기로 대체 불가)
- `ACTION_SEND` 리시버 (text/plain + video/*) — Voice2Tasks 패턴 재사용

### 9.1.1 동기화 대상 / 비대상

| 동기화함 | 동기화 안 함 (기기 로컬) |
|---|---|
| 일일 로그, 복습 큐, 문장 진행도 | 업로드 원본 영상 |
| 영상 계획, 전사 스크립트 | 녹음 파일 (용량) |
| 사용자 설정, 추천 풀 | |
| **L2 · L3 점수** | **L3에 보낸 녹음 원본** (점수만 남기고 버린다) |

> 녹음은 기기 로컬 보관이 원칙. 단 F-9용 **최초 녹음 1개만** Cloud Storage 동기화 대상으로 둔다.

### 9.2 백엔드 프록시 (최소 구성)

> **Gemini API 키를 APK에 넣지 않는다.** 개인용이라도 디컴파일 시 본인 키가 노출된다.

Cloud Run 프록시 책임 (개인용으로 축소):

- API 키 보관 — **Gemini + Azure Speech 둘 다**
- **Firebase Auth 토큰 검증 + 본인 이메일 화이트리스트 1개** (인증은 이것으로 충분)
- 파일 업로드는 **스트리밍 패스스루**로 설계 (메모리 버퍼링 금지).
  L3 녹음 중계도 같은 경로를 쓴다 — 녹음은 저장하지 않고 통과만 시킨다
- 추천 풀 배치 작업 호스팅 (Cloud Scheduler 1일 1회)

**제거된 항목**: 사용자별 rate limit, 사용량 계측 대시보드, 익명 기기 ID 발급
→ 단일 사용자이므로 불필요. 단 **Google Cloud 예산 알림은 설정**할 것

### 9.2.1 API 등급

| API | 등급 | 근거 |
|---|---|---|
| Gemini | **무료** | 유튜브 영상 1일 8시간 분량 상한은 1인 사용에 충분 |
| YouTube Data API | 무료 | 1일 10,000 units. 배치 1회만 쓰므로 여유 |
| Azure Speech (L3) | **무료 F0** | 월 5 오디오 시간. 일일 목표 300초면 월 2.5시간 (6.2절) |

> 세 API 모두 무료 등급 안에서 돌아간다. 단 예산 알림은 여전히 설정한다 —
> 무료 등급을 넘기는 순간을 **금액이 아니라 알림으로** 알아야 한다.

## 11. v1 출시 범위 제안

제품 정의(1절)가 **유튜브 기본 + 발음·횟수 카운트**이므로, 출시 순서는 그 두 축을 먼저 세운다.

### 11.1 단계

| 단계 | 범위 | 산출물 |
|---|---|---|
| **S0 — 루프 검증** | F-2 업로드 + L1 + F-3 예산 세션 + F-7 3단계 모드 | 외부 API 0개. 반복·카운트 루프가 손에 맞는지 확인 |
| **S1 — 기본 경로** | 프록시 + **F-1 유튜브** + 전사 + IFrame 재생 | 제품 형태 완성. 유튜브 URL 공유 → 세션 |
| **S2 — 발음 축** | L2(온디바이스) → **L3(Azure)** | "내 발음 카운트"의 실체 |
| **S3 — 지속** | F-6 복습 큐 → F-4 추천 | |
| **v2** | F-8 표현 은행, F-9 성장 기록, 원본 화자 음향 비교 | |

### 11.2 S0가 업로드 경로인 이유

유튜브가 기본 소재이지만 **첫 단계는 여전히 업로드 경로로 잡는다.** F-1은 Cloud Run 프록시 ·
Gemini 키 · Firebase Auth가 **전부 갖춰져야 한 줄이라도 돌아간다.** 반면 S0의 네 기능은
외부 의존이 0이라 하루이틀 안에 손에 쥘 수 있다.

> **다만 S0는 제품이 아니라 리허설이다.** 여기서 검증할 것은 "반복 세션이 지루하지 않은가,
> 3단계 완주가 카운트 단위로 적절한가"이고, 이 판단은 영상 출처와 무관하다.
> S0에서 멈추면 제품 정의를 만족하지 못한다 — **S1까지가 최소 출시선이다.**

### 11.3 순서 제약

- F-6(복습 큐)은 L2의 오답 판정을 입력으로 받는다 → **S2 이후**
- F-7(3단계 모드)은 외부 의존이 없다 → S0에 포함
- L3는 L2를 대체하지 않는다 → **L2를 먼저 세우고 L3를 얹는다** (6.3절 역할 분담)
- F-4(추천)는 배치 인프라가 필요하다 → 프록시가 선 뒤(S1 이후)
